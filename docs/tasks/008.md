# 008 — Revisão de contratos e segurança do backend

- Escopo: corrigir validação dos blocos de pedidos, leitura do cache serializado, consistência de paginação, idempotência de status e verificação JWT.
- Responsável: agente backend_review; coordenação e composição compartilhada pelo agente principal.
- Branch: `feature/008-validacao-backend`, worktree próprio a partir de `origin/develop`.
- Dependência: `feature/004-backend-api`, integrada localmente para implementar/revisar a API; sem merge remoto em develop.
- Propriedade: `backend/src/features/**`, `backend/src/shared/cache/**`, este registro. Configuração, bootstrap, banco/schema e scripts pertencem ao coordenador/outras tarefas.

## Alterações

- Criação exige objetos customer e deliveryAddress; substituição parcial rejeita null e arrays nesses blocos. País é normalizado antes da validação, como os demais textos.
- Paginação limita o índice para manter o offset aceito pelo banco; consulta de linhas e total usa snapshot RepeatableRead.
- Cache reidrata datas serializadas antes do mapeamento HTTP e ignora entradas com datas inválidas. A versão é revalidada antes de aceitar hits e antes de persistir resultados, reduzindo o uso de resultados de outra versão durante escrita concorrente.
- RN-07 permite repetir um estado final quando status é o único campo enviado; outras edições finais continuam proibidas.
- JWT aceita exclusivamente HS256 e exige claim de expiração numérica finita além de emissor, audiência e UUID público.

## Evidências

- `npm ci --prefix backend`: aprovado, 388 pacotes auditados, zero vulnerabilidades reportadas pelo npm.
- `make check`: aprovado; lint, geração Prisma, typecheck e build concluídos.
- Integração HTTP/banco/cache, cenários de concorrência e gates completos são responsabilidade da integração coordenada; não foram executados isoladamente nesta tarefa. Nenhuma suíte unitária foi criada, conforme docs/08.
- Casos encaminhados ao coordenador: segundo GET de listagem com cache real; criação sem blocos; PATCH com bloco null/array; repetição de status final; JWT assinado sem expiração.
- Cache continua opcional e sem promessa de linearização entre requisições concorrentes; alterações futuras de leitura em réplica devem preservar coerência entre versão e snapshot dos pedidos.
